======================================================================
RESUMO
======================================================================

C = Controller: recebe, aciona o Service, devolve status e corpo
S = Service: regra de negócio; lança exceção; não conhece HTTP
R = Repository: acesso ao banco
M = Mapper: converte Entity e DTO
DTO = o contrato da API

a requisição desce até o banco e a resposta sobe pelo mesmo caminho
código que sobe e funciona pode estar na camada errada

GABARITO
======================================================================

----------------------------------------------------------------------
PARTE 1
----------------------------------------------------------------------

a) Controller   b) Service   c) Repository
d) Mapper       e) Controller   f) Service

O método é do CONTROLLER: recebe a requisição (@PostMapping,
@RequestBody), aciona o Service e traduz o retorno em status (201) e
corpo. Não decide regra e não acessa o banco.

----------------------------------------------------------------------
PARTE 2
----------------------------------------------------------------------

1. {"id": 1, "login": "ana", "email": null}
   O DTO tem o campo email, mas o construtor usado só preenche id e
   login, então email fica null e aparece como null no JSON.
2. A senha não existe no DTO, então nunca sai.
3. O contrato da API é o DTO. Devolver a entidade expõe campos que a
   API não devia mostrar, mesmo que o Controller não altere nada.

----------------------------------------------------------------------
PARTE 3
----------------------------------------------------------------------

Quadro 1: resposta 400.
Com @Valid, o Spring confere o DTO antes de chamar o método; o título
em branco viola @NotBlank, então o Service nem roda.

Quadro 2: HTTP 404 com o corpo {"erro": "..."}.
O orElseThrow lança a exceção dentro do Service, o Controller nem
chega ao ResponseEntity.ok, e o handler global converte a exceção em
404. O Service só sinaliza o problema de negócio; quem traduz em
status é a camada web.

----------------------------------------------------------------------
PARTE 4
----------------------------------------------------------------------

A) A regra é conferida DEPOIS do save: o pedido inválido já foi
   gravado quando o erro sai. Mover o if para antes do save.

B) No SERVICE: consulta o Repository antes de salvar e lança exceção
   se o e-mail existir. A validação do DTO só enxerga o dado que
   chegou; o Controller não acessa o Repository.

C) O Controller fala direto com o Repository (pula o Service) e
   devolve a entidade (sem DTO). Correção: o Controller chama o
   Service, e o Service devolve List<ProdutoDTO> montada com o Mapper.

----------------------------------------------------------------------
PARTE 5
----------------------------------------------------------------------

Ordem:
 1 Spring lê o JSON e monta o DTO
 2 Controller chama o Service
 3 Service confere o e-mail
 4 Mapper converte DTO em entidade
 5 Repository grava
 6 Mapper converte a entidade em DTO
 7 Controller devolve 201 e o DTO

1. ANTES de o Controller rodar: o Spring valida o DTO ao montar o
   parâmetro.
2. No SERVICE (passo 3): ele lança a exceção e o handler global
   converte em 409.
3. Os passos 4 a 7: não converte, não grava e não devolve 201.

----------------------------------------------------------------------
PARTE 6
----------------------------------------------------------------------

1. (a) O Controller usa o Repository direto.
   (b) A regra (if do preço) está no Controller.
   (c) Entidade recebida e devolvida, sem DTO.
   (d) RuntimeException genérica vira 500 em vez de um status certo.
2. Service e Mapper (e o DTO).
3. @Positive no campo preco do DTO e @Valid no parâmetro do
   Controller: valor inválido devolve 400 antes de o Service rodar.

----------------------------------------------------------------------

1. public ClienteDTO buscar(Long id)

2. @NotBlank private String nome;

4. FALSO. O handler só conhece as exceções, não o Repository.
5. Controller -> Service -> Repository, com o Service também usando
